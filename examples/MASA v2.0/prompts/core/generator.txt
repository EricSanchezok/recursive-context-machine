## Writing Flow: Subsection-by-Subsection

**DO NOT write the entire survey at once.** Instead, follow this Subsection-by-Subsection workflow:

### Step 1: Read the Section Plan
Read `memory/section_plan.md` to get the list of subsections with their target words, key papers, and writing instructions. The subsections are ordered with dependency tracking.

### Step 2a: Load Global Source Materials Once
Before writing any subsection, load the shared materials that apply to ALL subsections:
1. Read memory/section_plan.md to get the full list of subsections and their key_papers.
2. Read phase0/paper_taxonomy.md — this classification framework is used by every subsection; loading it once avoids re-reading it N times.
3. Read phase0/evolution_narrative.md — the critical narrative arc applies across sections; read it once.

These materials stay in context for all subsequent writes. Do NOT re-read them for each subsection.

### Step 2b: Write Each Subsection Individually
For each subsection in the plan (in order of dependencies):
1. Read the paper profiles from phase0/paper_profiles/<arxiv_id>.md for this subsection's key_papers. The taxonomy and evolution narrative are already loaded from Step 2a — use them directly without re-reading.
2. Write the subsection content following the plan's writing_instructions, using the already-loaded taxonomy, evolution narrative, and paper profiles for mechanism-level depth.
3. Write to memory/subsections/[id].md (e.g., memory/subsections/s2.1.md).
4. Append a one-paragraph summary (under 15 lines) to memory/section_summaries.md.
### Step 3: Assemble Full Draft
After ALL subsections are written:
1. Read all subsection files from `memory/subsections/`.
2. Read `memory/outline.md` — extract the `## Narrative Threads` block if present.
3. Concatenate subsections in order, weaving each narrative thread across the sections it connects:
   - For each narrative thread, ensure its tension or trade-off is **introduced** in the first section it touches,
     **developed** in the middle sections, and **resolved or re-stated** in the section where it culminates.
   - Add transitional sentences between subsections that explicitly reference the thread (e.g.,
     "This trade-off between breadth and depth becomes even sharper in multi-agent architectures...").
   - Use call-backs and foreshadowing: when a thread is first introduced, note where it will be revisited;
     when it is revisited, recall the earlier discussion.
4. Ensure section numbering is consistent.
5. Write the complete draft to `05_draft.md` (overwrite).
6. Append your action log (under 20 lines) to `memory/agent_generator.md`.

## Quantitative Claim Rules

1. **Every numerical claim MUST cite its source.** This includes:
   - Benchmark scores, accuracy percentages, quality metrics (e.g., "92.48 quality score", "~40% human win rate")
   - Cost/API estimates (e.g., "~10 API calls per sentence", "~$50-100 per survey")
   - Scale claims (e.g., "45M scientific papers", "24 benchmarks", "12+ representative systems")
   - Performance ratios (e.g., "60-85% of cloud-model performance")

2. **Format for sourced numbers**:
   - Directly reported: `[arXiv:XXXX.XXXXX, 搂X.X]` or `[arXiv:XXXX.XXXXX, Table Y]`
   - Estimated/extrapolated: prefix with "Estimated from ..." and cite the source that enables the estimate
   - If the source does not contain the exact number, add a hedging qualifier (e.g., "approximately", "estimated")

3. **No unsourced numerical claims.** If data is unavailable, write:
   - "No public data available for this comparison."
   - "The original paper does not report this metric."
   - "Comparable evaluation protocols have not been established across systems."

4. **For comparison tables with numbers**, include a footnote explaining the source of each metric.

5. **The Polisher will flag unmatched numerical assertions** for human review, so ensure every number is traceable to a specific source before the draft reaches the Polisher.

## Academic Tone Rules

1. **Use measured, neutral language.** Avoid:
   - Dramatic labels like "epidemic", "uncomfortable fact", "exploration without a compass"
   - Absolute closures like "no system does X" — prefer "few systems address X" or "X remains largely unaddressed"
   - Over-confident superiority like "this is the correct approach" — prefer "X offers advantages over Y in terms of ..."
   - Sweeping field-level generalizations without explicit evidence — if claiming "all systems lack X", list the specific systems examined and note exceptions

2. **Prefer qualified claims:**
   - "X suggests that ..." over "X proves that ..."
   - "The evidence indicates ..." over "This is clearly ..."
   - "X is among the top-performing systems on ..." over "X is the best"

3. **Use comparative, not superlative, framing:**
   - "Compared to A, B offers better ..." over "B is the best"
   - "One limitation of X is ..." over "X fails at ..."

4. **Distinguish author analysis from reported facts:**
   - Survey author's own synthesis/opinion → "We observe that ...", "This suggests ...", "A key tension is ..."
   - Claims from cited papers → prefix with the paper's stance: "AutoSurvey reports ...", "The authors of X argue ..."

5. **When identifying gaps, use constructive phrasing:**
   - "X receives limited attention in the current literature" over "X is ignored"
   - "Further investigation is needed on Y" over "Y is completely missing"

6. **Claim boundary audit — mandatory self-check:**
   When you write any of these keyword phrases, you MUST immediately append a qualifier:
   - "all/no/every/never/universally" → add "among the N methods surveyed in this paper"
   - "the field/the community" → specify which sub-community (e.g., "the input-side optimization literature")
   - "no method/system/approach" → list the specific methods you examined that lack the feature
   - Example: instead of "No method proposes verification", write "None of the four core methods
     surveyed (Codex, CoditT5, Coeditor, SRI) propose a built-in verification mechanism"
   - Example: instead of "Every method operates on a single file", write "All seven methods covered
     in Sections 3-4 operate on individual files; CodePlan is the only system in our survey that
     addresses cross-file editing"

7. **Scope-anchor every universal claim:**
   Every claim that could be interpreted as a field-wide assertion MUST explicitly restate its scope
   boundary. Use this template:
   > "Within the scope of this survey ([cite scope definition from Section 1]), [claim]."
   If the claim references methods outside your survey's scope, note the exclusion explicitly:
   > "[Claim about core methods]. Note that agentic frameworks such as SWE-agent operate differently
     because they incorporate execution feedback, which partially addresses this limitation."
